Live static scan behavior

For a supported Windows PE executable, the scanner extracts file/optional-header values, section summaries, imports and other available static indicators. It then passes the extracted values to the fitted Random Forest pipeline. The model's fitted numeric median and categorical most-frequent imputers fill missing fields; the application reports those fields as unobserved, gives observed-feature coverage and marks the answer as a partial static estimate.

This allows inference when the scanner cannot observe runtime telemetry, but it does not recreate that telemetry. The model's top-ranked features include runtime process, file, registry and network observations. A partial prediction can therefore be unreliable and must be corroborated. The reported score is not calibrated probability and is not proof that a file is malicious or safe.

The fitted file-extension vocabulary contains exe; other extensions skip ML inference while static/YARA analysis can still complete. Unseen categorical values are ignored by the encoder and surfaced in the result.

What static inspection cannot observe

Actual registry operations, process creation, runtime network activity, API call sequences and memory behavior require dynamic instrumentation or an appropriate labeled telemetry source. A string that names an API or registry key does not prove that the behavior occurred. Such fields are never presented as measured activity.

Training metrics versus live performance

The saved metrics describe the notebook's reported random 8,000/2,000 split of the supplied dataset, including 99.10% accuracy. They are training artifacts, not a live scan benchmark. They do not establish that source/family leakage was excluded, that the test split represents deployment, or that outputs are calibrated. The model was trained on PE malware data separate from the EMBER2024 notebook.

Validation checklist

  1. Confirm model and schema paths in /api/model/readiness and check exact feature names/order.
  2. Use the pinned Python requirements, including scikit-learn 1.9.1.
  3. Review scan coverage, missing runtime features and unseen categories for each model result.
  4. Evaluate on a labeled, source/family/time-separated holdout representative of deployment; inspect false positives and false negatives.
  5. Report precision, recall, F1 and PR-AUC/ROC-AUC with denominators and class balance.
  6. Compare model, YARA and heuristic evidence separately; do not treat unlabeled production uploads as ground truth.
  7. Do not present training accuracy as live accuracy or model scores as calibrated probabilities.
